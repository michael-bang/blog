Adding an external execution node to an AAP installation running in OpenShift

01/07/2024 - Estimated reading time: 8 minutes — Ansible

Introduction

Many customers today have infrastructures with servers and equipment in many places. They have footprints on-premise and in the cloud and they may even have a large number of edge devices in places far away from where the core IT team is located. Security is also more important than ever and this has resulted in segmentation of the network and regulations on direction of traffic. Automation is therefore important to keep up with changes and risks.

Ansible Automation Platform version 2.1 (hereafter referred as AAP) introduced a new feature called Automation Mesh. The Automation Mesh provides two types of nodes: execution nodes and hub nodes. Execution nodes are for running the automation (workflows and job templates). Hub nodes connect the automation controller with execution nodes. It is possible to create your own mesh from these two types of nodes. The advantage of the Automation Mesh is that you can set up a mesh topology that matches your network design and get the execution nodes as close to where the automation is needed as possible. The Automation Mesh can help you in edge scenarios where network connectivity can be an issue or in situations where there is strict network security or other situations where you want to run the automation close to where it is needed.

AAP can be installed on OpenShift Container Platform through an operator which makes provisioning and management easy. The configuration can be done through Kubernetes manifest files that can be automated with Red Hat OpenShift GitOps. The AAP operator can get you up and running within a couple of minutes and provides features for day 2 operations as well.

AAP in OpenShift Container Platform is by default using pods started in the AAP namespace to handle the automation and have not had the Automation Mesh functionality from the beginning. This can make it difficult to run automation close to where the actual automation is needed and can be difficult in companies with strict security.

With version 2.3 of Ansible Automation Platform we made it possible to add execution nodes running on RHEL VMs (virtual or physical) connected to the Ansible Automation Controller running on OpenShift. Version 2.4 of Ansible Automation Platform extended this to also include the option to create hub nodes. These new options make it possible to run automation closer to the target of the automation, but still being managed by an automation controller running on OpenShift. This could help you in edge scenarios where network connectivity can be an issue or in situations where there is strict network security.

In the following I will show how you can add an external execution node controlled by an Automation Controller running in OpenShift.

Requirements

In order to run the following walkthrough, you will need Ansible Automation Platform on OpenShift version 2.3 or later, this example is running on version 2.4.

You will also need a machine running RHEL 8 or later that we will use to run the execution node. I’m running RHEL 9.2 on my machine. The RHEL host should be on a network that OpenShift can communicate with. In my example they are on the same subnet.

Red Hat Enterprise Linux - IP address 192.168.1.250
OpenShift Container Platform (Single node OpenShift) - IP address 192.168.1.27

Preparing the Ansible Automation Platform on OpenShift

You need to create a secret in the AAP namespace to hold the username, password and url for the registry.redhat.io. This is needed by Podman on the execution node to fetch execution environments. Create a secret called ee-pull-secret with the following. Exchange the values username and password with your information.

kind: Secret
apiVersion: v1
metadata:
  name: ee-pull-secret
  namespace: <The namespace where you have installed AAP>
data:
  Username: <Your username on registry.redhat.io>
  password: <your password on registry.redhat.io>
  url: registry.redhat.io
type: Opaque

Create it.

Go to the Operators -> Installed Operators and open the Ansible Automation Platform Operator. Go to the Automation Controller. Click on the three dots next to your aap controller and click Edit Automation Controller.

Add the following to the spec part:

ee_pull_credentials_secret: ee-pull-secret

Click save to update the configuration.

You are now ready to add an additional execution node.

Adding the execution node in AAP controller

Open the AAP web console and go to Administration -> Instances.

Click the Add button

Give the new instance a host name. The host name can either be a FQDN or an IP address like in my case. If you use a FQDN then be sure that it is resolvable from your OpenShift environment. Set the port that Receptor should be listening on (default port 27199). It is possible to create both hub and execution nodes. In this case I’m creating an execution node that should be connected to the control node and you will therefore need to set the “Peers from control node” option.

Click save to create the execution node configuration. The status of the execution node will be “installed” and there is an “Install bundle” link as shown below.

Click next to the “Install Bundle” to download the tar ball that is needed for the installation on the RHEL machine.

Prepare the RHEL machine

ou will need to add the repository for ansible in my case:

sudo subscription-manager repos --enable ansible-automation-platform-2.4-for-rhel-9-x86_64-rpms

Install ansible-core

sudo dnf install ansible-core

You need to install the ansible.receptor collection:

ansible-galaxy collection install ansible.receptor

You need to be able to connect to the RHEL machine with an SSH key. I will not go through the process in this document.

You are now ready to install the execution node (Receptor service) on the RHEL machine.

Installing the Execution node

Ensure that you have the tar ball (that you downloaded earlier from the AAP console) in the current directory on the RHEL machine. Run:

tar xvf <name of tar.gz file>
cd <name of bundle>

You need to update the inventory.yml file:

---
all:
  hosts:
    remote-execution:
      Ansible_host: 192.168.1.250
      Ansible_user: <username> # user provided
      Ansible_ssh_private_key_file: ~/.ssh/id_rsa # private key file

The ansible_host variable is set to the name of the execution node you entered earlier and you need to set the ansible_user to the user you want to do the installation with and a path to the private key to access the host with. Save the file.

To run the installation use:

ansible-playbook -i inventory.yml install_receptor.yml

If you need to enter a password when running sudo with the user added as installation user you will need to have the “–ask-become-pass” added to the command.

The output should be similar to the following:

PLAY [all] *********************************************************************************************************

TASK [Gathering Facts] *********************************************************************************************
ok: [remote-execution]

// details skipped //

PLAY RECAP *********************************************************************************************************
remote-execution           : ok=58   changed=26   unreachable=0    failed=0    skipped=9    rescued=0    ignored=0

The Receptor service should now be running. You can check that with:

Systemctl status receptor

Opening receptor port in firewall

I needed to add the receptor port to the firewall configuration in order to get the Automation Controller to connect to the execution node. Run the following command to add the receptor port (may be different if you changed the default port):

sudo firewall-cmd --add-port=27199/tcp --permanent

Installing ansible-runner

I also needed to install ansible-runner. You can use the following command to do that.

sudo pip3 install ansible-runner

Using the new execution node

Before running any workload on the newly added execution node we need to check the status of the node.

Go to the instance that you created Administration -> Instances and click on the instance.

Create an instance group

In order to ensure that your automation is run from the newly created execution node you need to create an instance group.

Go to Administration -> Instance Groups and click add -> Instance group

Give the instance group a name like “remote-exe” and then click on Save.

Go to the instances tab and click on Associate.

Select the newly created execution node and click on Save.

You now have an instance group that you can use with workflows and job templates.

Running the first template

Go to Resources -> Templates and click Add -> Job Template

Give the template a:

Name: Test
Inventory: Demo Inventory
Project: Demo Project
Playbook: hello_world.yml
Instance Groups: remote-exe

Then click Save.

Now click on Launch to start the Test template.

You now have a running external execution node you can use to run automation outside of OpenShift.

Conclusion

This walkthrough showed you how to add an external execution node to an automation controller running on OpenShift. This could help you in edge scenarios where network connectivity can be an issue or in situations where there is strict network security.
